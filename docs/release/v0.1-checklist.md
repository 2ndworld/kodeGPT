# KodeGPT v0.1 Release-Candidate Checklist

This checklist separates deterministic local/CI evidence from external ChatGPT-host evidence. A release candidate may be technically complete while the final compatibility claim/tag remains blocked on host evidence.

## Toolchain floor

- Node.js: 24
- pnpm: 10.15.0
- Rust: stable, minimal profile
- Bubblewrap: 0.11.2, exact accepted source commit `1b80120ef26a28e065e67f89bfef873f13bdd317`
- Bubblewrap production/CI binary metadata: root-owned, mode `0755`, non-setuid
- Ubuntu 24.04 CI: use the targeted `/etc/apparmor.d/bwrap-userns-restrict` profile for `/usr/bin/bwrap`; never disable the global AppArmor unprivileged-userns restriction merely to make sandbox tests pass
- MCP protocol: `2026-07-28`
- KodeGPT MCP semantic surface: `0.3`

## Verification intent levels

The release matrix remains substantive; focused suites are not deleted merely because `pnpm test` may overlap them. Use the levels below to make the reason for each run explicit:

- **Focused development gate:** changed package/unit tests plus the directly affected integration/security suite and `pnpm verify:forbidden` when authority-bearing code changed. This is fast RED/GREEN feedback, not release evidence.
- **Candidate gate:** the complete deterministic command gate below on the exact candidate tree, including explicitly named protocol/integration/security/isolation/acceptance/Rust/package gates even when some tests overlap the full TypeScript suite. Each named gate carries a distinct release/security intent.
- **Final integration gate:** candidate gate on the exact final SHA, CI success for that SHA, complete `main...feature` diff review, real local installed-service cutover/provenance proof when the service lifecycle changed, and the bounded ChatGPT smoke required by `docs/verification/host-acceptance.md`.

Do not optimize elapsed time by removing substantive coverage. If an exact duplicate invocation is retained, its justification must be that it represents a distinct named gate, not habit.

## Deterministic candidate command gate

Run from the KodeGPT worktree/release candidate with a frozen dependency graph:

```text
pnpm install --frozen-lockfile
cargo fmt --all -- --check
pnpm run typecheck
pnpm build
pnpm test
cargo test -p kodegpt-sandbox
pnpm test:rust
pnpm test:protocol
pnpm test:integration
pnpm test:security
pnpm test:isolation
pnpm test:acceptance
pnpm verify:forbidden
pnpm verify:package
pnpm bench:baseline
```

Requirements:

- Every command exits zero.
- Bubblewrap functional tests are executed, not skipped because a host prerequisite is missing.
- Security acceptance does not downgrade a missing/invalid Bubblewrap environment to a passing skip.
- Package smoke installs into a clean temporary HOME/prefix and verifies release-runtime checksums.
- When the local service lifecycle is in scope, package smoke must additionally stage a service release outside both the source checkout/worktree and the clean package prefix, verify the installed Rust checksum, render a secret-free user unit, report sanitized status through a fake service manager, and uninstall without touching general KodeGPT state.
- Performance baseline uses 5 warmups and 30 measured iterations and is record-only: latency numbers are not a release pass threshold in v0.1.

## Architecture absence review

Before release, verify all remain absent:

- public capability IDs (`kc_...`) or private execution IDs (`ex_...`) in MCP output;
- host spool paths in artifact metadata;
- public shell-string execution such as `shell.run`;
- MCP service lifecycle mutation such as `service.install`, `service.start`, `service.stop`, `service.restart`, or `service.uninstall`;
- installed-service unit/runtime paths that point into a Git checkout or feature worktree;
- connector token/verifier, zrok account secret, raw zrok status payload, or sensitive environment in service metadata/unit/status output;
- TypeScript filesystem/user-process fallback behind kernel-owned boundaries;
- `child_process.exec`/`execFile` user execution fallback;
- workspace authority passed to Bubblewrap by host pathname instead of retained FD;
- canonicalize-then-open security-sensitive workspace I/O;
- dynamic executable extension imports/eval;
- MCP v1 SDK/server compatibility imports;
- `@modelcontextprotocol/ext-apps/server`, `registerAppTool`, or `registerAppResource` in mcp-server;
- authored flat `ui/resourceUri` metadata;
- initialize-time cached Apps support state;
- `Mcp-Session-Id` or accepted legacy session/SSE paths;
- deprecated `vitest.workspace.*` configuration.

`pnpm verify:forbidden` is the executable guard for these authored product-code constraints. Tests/docs/generated UI bundles are excluded from product-behavior matching so negative assertions do not create false positives.

## Pranikah isolation gate

The complete local final command set must be enclosed by passive Pranikah snapshots written outside the Pranikah repository:

```text
node scripts/host-compatibility-checklist.mjs capture --pranikah-root <pranikah-root> --output <local-before-json>
# run complete KodeGPT final command set
node scripts/host-compatibility-checklist.mjs capture --pranikah-root <pranikah-root> --output <local-after-json>
node scripts/host-compatibility-checklist.mjs compare --before <local-before-json> --after <local-after-json>
```

The compare command must exit zero. A changed protected repository/listener state is a hard failure; do not weaken the guard or modify Pranikah to make it pass. Machine-specific guard snapshots remain local-only.

## ChatGPT host claim gate

Deterministic MCP conformance is **not** equivalent to a real ChatGPT host observation. Use `docs/compatibility/chatgpt.md` and `tests/host/README.md` for the manual evidence contract. For the managed personal/development path, the release candidate must be exercised through `kodegpt expose zrok --name <namespace:name>` using a pre-existing reserved zrok v2 name, and the exact connection path must be recorded as `zrok-public-https-query-credential`.

Claim states are granular rather than all-or-nothing:

- `DETERMINISTIC_MCP_PASS`: allowed only after security/protocol/Apps acceptance is fresh and green.
- `CHATGPT_HOST_OBSERVED`: allowed only after the actual target ChatGPT plan/workspace discovers and invokes KodeGPT through its supported connection path.
- `WRITE_OBSERVED`: allowed only after the target host actually exposes and successfully completes the tested reversible write/edit round trip.
- Skill **action exposure** may be recorded when the three read-only skill actions reach KodeGPT, but that is not evidence of a positive configured-catalog round trip.
- Positive skill-host compatibility requires a non-empty `skill.list -> skill.inspect -> skill.load` sequence with the expected resource marker verified.
- MCP Apps rendering is a separate observed category and may remain unobserved even when semantic tools/text fallback pass.

For every unobserved category, keep its field false/pending. Do not infer a host PASS from local MCP tests, server annotations, `host.uiSupported`, another plan/workspace, or documentation.

Fresh capability-quality verification on 2026-08-13 established behavior/source candidate `46d98ee`, then preserved the final regression-assertion candidate as `5f5039e` (`test(mcp): assert skill.list compatibility schema`). Fresh ChatGPT host inventory then directly reported semantic surface `0.3` and exposed optional `skill.list.compatibility` with the four contract enum values. PR #4 merged that exact candidate tree into `main` as `64c203dba81b1bfede183ece59467eaf7bad26e0`, after which the required exact-main verification and host smoke remained green.

## Tag gate

Do **not** create the v0.1 tag until all of the following are true for the exact commit being tagged:

- deterministic command gate: PASS;
- package clean-install gate: PASS;
- security + MCP/Apps acceptance: PASS;
- final Pranikah isolation compare: PASS;
- manual ChatGPT host evidence: captured for the target plan/workspace and connection path;
- release claims: scoped only to capabilities actually observed on that host;
- working tree/release commit reviewed and final CI green.

The host-evidence gate is satisfied only for categories actually captured on the target host. Unobserved categories such as Apps rendering or a positive configured-catalog skill round trip remain explicitly pending claims; they do not become PASS by inference, and release/tag prose must not claim those capabilities as host-observed.
